设计可演示的任务闭环、失败恢复和评测产物，让技术主张对应明确证据。

<!--more-->

> 本文为计划于 2026-09-16 发布的草稿，初稿整理于 2026-09-12。示例为方案设计，参数用于说明方法，不代表已上线项目或实测成果。

## 展示目标是一条可以检查的证据链

技术博客可以解释设计，但不能单独证明系统已经实现。要把这套文章发展成作品集，可以围绕一个最小任务闭环准备代码、运行方式、评测和故障恢复记录。

本篇是后续实施计划。当前博客仓库只包含文章，不把文中的目录、接口或指标当作已经存在的项目成果。

## 最小演示包含正常与异常两条路径

正常路径是：用户查询规范，得到带引用的回答，准备工单并确认创建。异常路径是：创建接口成功后丢失响应，系统重启并通过原操作 ID 核实结果。

只展示正常问答，难以体现 Java 后端优势。一个能解释租约、幂等和对账的异常演示，更容易连接架构能力和 Agent 应用。

同时准备第二个租户，证明隔离由服务端实现；演示权限撤销后，旧答案和旧引用不能继续使用。

## 每项主张对应一个产物

| 技术主张 | 需要的证据 | 尚未完成时如何表述 |
| --- | --- | --- |
| 工具写入具备幂等性 | 重复请求测试与下游唯一记录 | 已设计幂等方案，待验证 |
| RAG 可隔离租户 | 两租户样本与检索日志 | 已定义权限边界 |
| 任务可以恢复 | 崩溃注入脚本和状态时间线 | 已完成恢复流程设计 |
| 检索策略有效 | 同样本对照结果和原始数据 | 提出混合检索实验计划 |
| 容量达到目标 | 配置、负载模型和完整报告 | 仅完成容量估算 |

证据不需要华丽，但必须能对应主张。截图可以帮助阅读，机器可读取的原始结果更适合复查。

## 演示仓库可以这样组织

~~~text
docs/         架构图、ADR、运行前提
app/          任务与业务入口
worker/       编排与恢复
fixtures/     合成知识和租户数据
evals/        固定样本与评判脚本
experiments/  检索对照、负载和故障注入
results/      带版本的原始结果与摘要
~~~

这是建议结构，不要求立刻拆成多个构建模块。最小启动说明应列出 JDK、依赖版本、环境变量名称和模拟模式。仓库不包含真实 token 或内部文档。

优先提供离线模拟模型和工具，使评审者不配置付费模型也能验证任务状态机。真实模型模式用于观察回答质量，两种模式的结果分开标注。

## 用十分钟讲清楚项目

前两分钟说明场景、用户和成功条件；三分钟展示完整任务；两分钟触发响应丢失并恢复；两分钟查看评测失败案例；最后一分钟解释一个架构取舍。

避免花一半时间介绍框架安装。评审者更需要看到：失败状态是否明确、系统是否越权、重复执行如何处理，以及哪些部分仍未完成。

## 评测报告保留失败

参考 [Agent 评测的分层思路](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，可以同时展示确定性终态断言和回答质量判断。结果写明样本量、模型与提示词版本、重复次数和限制。

如果只测试了 40 个合成案例，就写清楚是 40 个合成案例。不要将其扩写成“大规模企业落地验证”。没有真实用户时，也不编造 DAU、节省人力或生产 QPS。

完成这些产物后，博客可以通过真实链接连接到代码和实验。文章负责解释思路，仓库负责证明实现，评测负责呈现边界，三者各自承担清楚的角色。
